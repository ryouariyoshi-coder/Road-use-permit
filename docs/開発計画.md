# MVP開発計画：道路使用許可申請書作成ツール

## 1. この計画の目的

[課題仮説シート.md](./課題仮説シート.md)、[spec.md](./spec.md)、[WBS.md](./WBS.md)をもとに、全機能を一度に開発せず、現場担当者の作業体図作成の負担を減らせるかを確認するMVP（最小限の実用版）の計画をまとめる。

アプリの成果物は `index.html` 1ファイルとする。日程・担当者・工数は未定のため、本計画では作業順序と完了条件を定める。

## 2. MVPの狙い

現場担当者が現在Excelで行っている、背景図への作業アイテム配置と寸法記入の手間を減らし、申請書類一式を作成してA4で出力できるかを実際の業務例で確かめる。

課題仮説シートでは、作業体図作成が週4～5回発生し、図形や寸法を一つずつ手作業で配置・記入すると確認されている。そのため、MVPでは自動取得機能を広く作り込むより、作業体図の編集を中心に、書類の完成・出力までを一通り試せることを優先する。

## 3. MVPに含める範囲

### 3.1 現場データと申請書

- 住所を入力して現場データを作成する。
- 住所以外の申請情報を入力し、提出用の申請書表紙に表示する。
- 申請書上の文字を直接編集できる。
- 提出先警察署名は利用者が入力・修正する。住所からの全国自動判定はMVPに含めない。

### 3.2 地図・写真

- 住所からGoogleマップを別画面で開く導線を用意する。
- 利用条件が確認できた画像、または利用者が用意した画像を取り込み、地図・写真台帳に配置する。
- 左右方向の全景写真をそれぞれ取り込める。
- 外部サービスの画像を無断で取得・保存・再配布する機能は作らない。利用条件を確認できない場合は、その画像をMVPの入力元として扱わない。

### 3.3 作業体図

- 利用者が用意した平面図、または使用条件を確認できた地図画像を背景として取り込む。
- カラーコーン、バー、作業車両などの基本アイテムを選択して配置する。
- アイテムの移動、サイズ・向きの変更、削除をできるようにする。
- 縮尺の設定方法を先に小さく試作・評価してから決定し、背景上の寸法とmm表示を対応させる。
- 100mm刻みの寸法設定と、図形の変更に合わせた寸法表示の自動更新を実装する。
- 画面上で拡大・縮小して編集できる。

### 3.4 保存と出力

- 保存ボタンで複数現場のデータを同じパソコンの同じブラウザー内に保存し、一覧から再開できる。
- 書類をブラウザーの1ページ内に表示する。
- 申請書、地図、写真台帳、作業体図をそれぞれA4で印刷、またはPDF保存できる。
- ChromeとEdgeで基本動作を確認する。

## 4. MVPに含めないもの（後続候補）

- 住所からの地図画像・ストリートビュー画像の自動取得や、画像の角度変更をアプリ内で直接行う機能
- 住所から提出先警察署を全国一律に自動判定する機能
- サーバーを使った複数端末・複数社員間の共有や同時編集
- 過去の申請データを使った自動作図、テンプレートの高度な再利用
- 申請書類以外の追加帳票や、MVP試行で必要性が確認されていない高度な編集機能

これらはMVP試行の結果と、利用条件・データの入手可能性を確認してから優先順位を決める。

## 5. 開発ステップと完了条件

| 段階 | 作業 | 完了条件・判断 |
|---|---|---|
| 0. MVP要件を確定 | 最新の申請書様式と必要書類、地図画像の利用条件、縮尺設定案、保存上限、利用者の試行方法を確認する | 実装してよい画像入力方法と、MVPの受入条件が決まっている。縮尺は実寸が分かる例で試作案を比較し、利用者が選べる |
| 1. 画面と基本データを作る | 1ページの構成、現場データの項目、申請書の直接編集、機能ごとのコード分割を実装する | 住所と申請情報を入力し、申請書の表示に反映できる |
| 2. 添付資料を作る | 地図リンク、画像の取り込み、地図・左右の写真台帳への配置を実装する | 条件を確認した画像を画面上で確認・差し替えできる |
| 3. 作業体図を作る | 背景画像、縮尺、基本アイテム編集、100mm刻みの寸法と自動更新、拡大縮小を実装する | 実寸が分かるテスト図で寸法が合い、図形変更に寸法表示が追従する |
| 4. 保存・出力を作る | ブラウザー内の複数現場保存・再開、書類ごとのA4印刷・PDF保存を実装する | 保存後に再読込して内容・画像・図形が保たれ、各書類を個別に出力できる |
| 5. 検証・試行 | Chrome・Edgeで確認し、匿名化した実例を使って現場担当者に試してもらう | 重大な提出書類の欠落や寸法誤りがなく、所要時間・つまずき・要望を記録し、MVP継続判断ができる |

各段階の終了時に、成果物と受入条件を確認してから次の段階へ進む。外部画像の利用条件、申請様式、縮尺精度のいずれかに問題があれば、その問題を解消するまで該当機能の実装・試行を進めない。

## 6. MVPの受入・評価方法

- **業務時間**：住所入力を始めてから、必要書類をA4印刷またはPDF保存できるまでを測る。10分以内をMVPの目標とし、5分は改善目標として別に記録する。
- **作業体図**：寸法が既知のテスト図と現場担当者の確認により、縮尺・100mm刻み・寸法自動更新が正しいことを確認する。
- **書類品質**：最新の様式・提出例と照合し、必要項目、配置、画像の判読性を確認する。提出前に利用者が内容を確認する前提とする。
- **利用性**：担当者が作図の配置・修正、画像の取り込み、保存・再開で迷った点を記録する。
- **ブラウザー**：ChromeとEdgeそれぞれで、編集、保存・再開、A4印刷・PDF保存を確認する。
- **試行データ**：初期試行では個人情報・機密情報を含まないサンプルを使う。実データを使う場合は社内IT部門の確認を先に得る。
- **試行人数・件数**：現場担当者3～5名、各自2～3件を目安とする提案。実施可能な人数と案件は開始前に調整する。

目標時間に届かない場合も、未達だけで判断せず、作業体図・画像準備・申請情報入力のどこに時間がかかったかを分けて記録する。結果をもとにMVPを修正するか、後続機能へ進むかを判断する。

## 7. 主なリスクと対応

- **外部画像の利用条件**：スクリーンショット等の取得や提出書類への掲載が認められるとは限らない。サービスごとの条件を事前確認し、確認できた画像または利用者が適切に用意した画像だけを扱う。
- **縮尺の誤り**：図の見た目だけで実寸を保証できない。実測値を使った縮尺設定とテストを必須にし、精度を検証する。
- **警察署の自動判定データ不足**：全国分の情報が無料で利用できるか未確認のため、MVPは手入力で処理を止めない。
- **ローカル保存の容量・消失**：画像を含むデータの保存上限や、ブラウザーのデータ消去による消失リスクを表示・確認する。重要データの唯一の保管先として扱わない。
- **申請書の誤記・様式更新**：最新様式との照合と、提出前の利用者確認を行う。

## 8. MVP後の判断

試行結果をもとに、次の順で追加開発の優先度を決める。

1. 作業体図で繰り返し発生した使いづらさ・寸法精度の改善
2. 住所からの資料準備の自動化（利用条件を満たす方法がある場合）
3. 警察署名の自動判定（信頼できる全国情報を使える場合）
4. 既存データの再利用など、試行で効果が確認された機能
5. 共有・同時利用は、社内IT部門と経営層による必要性・リスク評価後に別途判断
